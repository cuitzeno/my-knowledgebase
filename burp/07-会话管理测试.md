# 会话管理测试：令牌强度、Cookie、会话固定、CSRF

## 一句话定义
会话测试四问：**令牌够乱吗** → Sequencer 分析熵、**Cookie 属性对吗** → HttpOnly/Secure/SameSite、**登录后换新吗** → 会话固定、**请求带 CSRF token 吗** → 跨站请求伪造。

## 核心架构 / 工作原理

```mermaid
graph TD
  A[会话管理四大测试] --> B[令牌强度 Token Strength]
  B --> B1[采集 1000+ 样本: 登录/刷新/重登]
  B --> B2[Sequencer 分析: 字符级/位级熵、字符分布、相关性]
  B --> B3[判定: 有效熵 < 64 bits = 弱 / < 128 bits = 中 / >= 128 bits = 强]
  
  A --> C[Cookie 安全属性]
  C --> C1[HttpOnly: 防 JS 读 document.cookie]
  C --> C2[Secure: 仅 HTTPS 传输]
  C --> C3[SameSite: Strict/Lax/None 抗 CSRF]
  C --> C4[Path/Domain: 最小权限原则]
  C --> C5[Expires/Max-Age: 合理过期]
  
  A --> D[会话固定 Session Fixation]
  D --> D1[登录前 Session ID = S1]
  D --> D2[登录后 Session ID = S2]
  D --> D3[S1 == S2 -> 存在固定风险(攻击者预置 S1 诱导受害者登录)]
  D --> D4[修复: 登录后必须重新签发新 Session ID]
  
  A --> E[CSRF 跨站请求伪造]
  E --> E1[关键请求无不可预测 token]
  E --> E2[Cookie 自动携带 + 无同源校验]
  E --> E3[SameSite=None 且无 CSRF token]
  E --> E4[测试: 构造恶意页面自动提交表单/发 AJAX -> 受害者访问即中招]
```

| 测试项 | Burp 工具 | 核心操作 | 通过标准 |
|--------|-----------|----------|----------|
| **令牌强度** | Sequencer | 选请求 → Send to Sequencer → Start live capture(1000+) → Analyze | 有效熵 ≥ 128 bits；字符分布均匀；无相关性 |
| **Cookie 属性** | Proxy/Repeater + 手工检查 | 登录响应 Set-Cookie 头 → 看 HttpOnly/Secure/SameSite/Path/Domain | 关键 Cookie 全勾选 HttpOnly+Secure+SameSite=Lax/Strict |
| **会话固定** | Repeater/Proxy | 1) 访问登录页拿 Session ID → 2) 登录 → 3) 对比前后 Session ID | 登录前后 Session ID **必须不同** |
| **CSRF** | Repeater/浏览器 | 1) 找关键操作(改密/转账/删数据) → 2) 看请求有无 token → 3) 无 token 造 PoC 页测 | 所有修改状态的请求必须带不可预测 CSRF token |

## 快速上手步骤

1. **测令牌强度**：
   - 登录一次 → Proxy HTTP history 右键登录响应/后续请求 → Send to Sequencer
   - Sequencer 标签 → 配置：Token location(Cookie/Header/Body 正则) → Start live capture → 等 1000+ 样本
   - Analyze → 看 Overall score / Character-level entropy / Bit-level entropy / Character distribution chart
2. **测 Cookie 属性**：
   - 登录 → Proxy HTTP history 找登录响应 → Response headers 找 `Set-Cookie`
   - 逐条检查：`HttpOnly` `Secure` `SameSite=Strict/Lax` `Path=/` `Domain=.example.com` `Max-Age=3600`
   - 缺失项记录为 Finding
3. **测会话固定**：
   - 新隐身窗口 → 访问登录页 → 开发者工具 Application 记录 Session Cookie 值 S1
   - 正常登录 → 记录登录后 Session Cookie 值 S2
   - 对比：S1 == S2 → **高危：会话固定**；S1 != S2 → 通过
   - 进阶：用攻击者账号预置 S1 → 诱导受害者登录 → 攻击者用 S1 访问 → 看是否蹭上会话
4. **测 CSRF**：
   - 列出所有修改状态接口(改密、改邮箱、转账、删数据、发帖、加好友)
   - 每个接口抓请求 → 看 Body/Header/Cookie 有无 `csrf_token` `_token` `X-CSRF-Token` `X-Requested-With`
   - 无 token → 构造 HTML PoC：`<form action="https://target.com/change-pass" method="POST"><input name="newpass" value="hacked"><input type="submit"></form>` → 受害者访问自动提交
   - SameSite=Lax/Strict 可缓解 GET 型 CSRF，POST 型仍需 token

# Sequencer 批量采集脚本思路(配合宏/扩展)
for i in range(1000):
    login()  # 或刷新 token
    token = extract_session_token()

## 踩坑避坑指南

| 场景 | 问题现象 | 原因 | 解决/最佳实践 |
|------|----------|------|---------------|
| 令牌长就以为安全 | 64 字符但全是时间戳/自增 | 熵低可预测 | **必须看 Sequencer 熵分析**，不看长度看随机性 |
| 只检查 HttpOnly | 忽略 SameSite/Secure | 认知不全 | **四项全查**：HttpOnly(防 XSS 偷) + Secure(防 MITM) + SameSite=Strict/Lax(防 CSRF) + Path/Domain 最小化 |
| 登录后 Session ID 变了就以为安全 | 忽略并发/多标签/刷新场景 | 固定可能在特定流程 | 多场景测：正常登录、记住我、SSO 回调、OAuth 回调、密码重置后、多标签并发登录 |
| SameSite=Lax 以为万无一失 | POST CSRF 依然可行 | Lax 只保护 GET/顶级导航 | **关键操作必须显式 CSRF token**，不依赖 SameSite |
| Token 放在 URL | 以为有 token 就安全 | URL 会泄露在日志/Referer/历史记录 | CSRF token **必须放 Body 或自定义 Header**，不可放 URL |
