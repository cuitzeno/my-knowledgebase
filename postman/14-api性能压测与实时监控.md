# Postman 实战｜API 性能：负载压测与实时监控

功能对、安全稳，还得"扛得住"。这篇讲用 Postman 11 的性能/负载测试与 Monitor，给 API 做压力与长期体检。

## ① 是什么

- **性能测试**：看接口在不同负载下的响应时间、吞吐量、错误率。
- **负载/压测**：逐步加压直到拐点，找出系统能承受的并发上限。
- **Monitor（监控）**：定时跑集合，长期盯住可用性与耗时，异常就告警。

## ② 为什么重要

- 功能测试通过≠上线不卡；真实流量一来，慢查询、连接池耗尽就暴露。
- 不监控，故障往往是用户先发现。Monitor 让你比用户早知道。

## ③ 核心概念拆解

- **Postman 性能测试（Postman 11 新能力）**：基于集合做负载测试，模拟多虚拟用户并发，报告出响应分布与错误率，判断能否扛真实流量。
- **Newman 做简单压测**：用脚本循环/并行 `newman run` 近似加压，适合轻量场景（重压仍建议专业工具）。
- **Monitor 设置**：选集合+环境，设频率（如每 5 分钟）与地域，失败/超时触发通知（邮件/Slack）。
- **看指标**：关注 p95/p99 响应时间、错误率、吞吐量；设阈值告警。

## ④ 常见误区

- **误区 1**：只在本地单线程点一下就算性能 OK。要模拟并发。
- **误区 2**：压测打生产。应在预发/压测环境，避免影响真实用户。
- **误区 3**：监控只看"通不通"。响应变慢也是病，要盯耗时趋势。

## ⑤ 一句话小结

用 Postman 11 负载测试找并发拐点，用 Monitor 长期盯可用性与耗时——性能与稳定都要有数据撑腰。
