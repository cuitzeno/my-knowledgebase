# Web 缓存与缓存投毒

## 一句话定义
缓存让网站变快，但配置不当会变成"投毒"通道——把恶意响应存起来发给所有用户。核心成因：**缓存键 ≠ 影响响应的输入**，攻击者借未键入输入改变响应并被缓存。

## 核心架构 / 工作原理

```mermaid
graph TD
  A[缓存投毒成因] --> B[缓存键 Cache Key]
  B --> B1[通常: URL + Host + 少量头]
  B --> B2[决定"哪些请求算同一个"]
  
  A --> C[未键入输入 Unkeyed Input]
  C --> C1[影响响应但不在缓存键中的头/参数]
  C --> C2[如: X-Forwarded-Host, User-Agent, X-Original-URL]
  
  A --> D[投毒链路]
  D --> D1[攻击者发请求含恶意未键入输入]
  D --> D2[服务器响应含恶意内容(如重定向/注入脚本)]
  D --> D3[响应被缓存(匹配缓存键)]
  D --> D4[受害者命中缓存 -> 拿到恶意响应]
```

| 关键概念 | 说明 | 典型例子 |
|----------|------|----------|
| **缓存键** | 决定缓存命中的字段集合 | `URL + Host + Accept-Encoding` |
| **未键入输入** | 影响响应但不在缓存键中的输入 | `X-Forwarded-Host` `User-Agent` `X-Forwarded-Proto` |
| **投毒载荷** | 经未键入输入注入响应的恶意内容 | `<base href="https://evil.com">` `Location: https://evil.com` |
| **设计缺陷型** | 不安全重定向/动态拼接被缓存放大 | `Location` 头用未键入 Host、错误页回显输入 |

## 快速上手步骤

1. **识别未键入输入**：
   ```bash
   # 发请求加各种头，看响应是否变化
   curl -H "X-Forwarded-Host: evil.com" https://target.com/
   curl -H "X-Original-URL: /malicious" https://target.com/
   curl -H "User-Agent: <script>alert(1)</script>" https://target.com/
   ```
2. **验证缓存命中**：
   ```bash
   # 看响应头判断是否命中缓存
   curl -I https://target.com/ | grep -iE "cache|age|cf-ray|x-cache"
   # 命中特征: Age > 0, X-Cache: HIT, CF-Cache-Status: HIT
   ```
3. **构造投毒请求示例**：
   ```http
   GET /en HTTP/1.1
   Host: vulnerable.com
   X-Forwarded-Host: evil.com          <- 未键入，但被拼进响应里的 <base href>
   
   HTTP/1.1 200 OK
   Cache-Control: public, max-age=3600 <- 被缓存
   <html><base href="https://evil.com">... <- 后续受害者命中缓存拿到此页
   ```
4. **防御清单**：
   - 收敛缓存键：把影响响应的头加入缓存键(CDN/WAF 配置)
   - 禁用动态响应缓存：`Cache-Control: private, no-store` 用于个性化/认证页面
   - 净化未键入输入：服务端不直接把 `X-Forwarded-Host` 等拼进响应
   - 谨慎缓存重定向/错误页：`Cache-Control: no-store` 或加入 Vary 头

```bash
# 快速测试未键入输入
for h in "X-Forwarded-Host" "X-Forwarded-Proto" "X-Original-URL" "X-Rewrite-URL" "User-Agent"; do
  echo "Testing $h..."
  curl -H "$h: evil.com" -s -o /dev/null -w "%{http_code} %{size_download}\n" https://target.com/
done
```

## 踩坑避坑指南

| 场景 | 问题现象 | 原因 | 解决/最佳实践 |
|------|----------|------|---------------|
| 以为缓存只存静态资源 | API/带参数页面也被缓存 | CDN 默认缓存策略过宽 | **显式控制**：认证/个性化页面 `Cache-Control: private, no-store` |
| 有缓存就快且安全 | 未键入输入是经典投毒温床 | 缓存键与响应影响因子错位 | **审计所有影响响应的头/参数** -> 要么加入缓存键、要么净化、要么禁缓存 |
| WAF 能挡投毒 | 投毒是逻辑/配置问题，WAF 常看不到 | WAF 匹配特征非逻辑 | **源头治理**：收敛缓存键 + 净化输入 + 禁缓存动态响应 |
| Vary 头用错 | `Vary: User-Agent` 导致缓存碎片化/失效 | 过度 Vary | **精准 Vary**：仅对真正影响响应的头(如 `Accept-Encoding`) |
| 错误页被缓存 | 5xx/404 页被缓存 -> 用户全看到错误页 | 错误响应默认可缓存 | **错误页 `Cache-Control: no-store`** 或极短 `max-age` |

## 替代方案对比

| 维度 | 缓存投毒防御 | WAF 规则 | CSP | 代码级输出编码 |
|------|--------------|----------|-----|----------------|
| 防御层面 | 配置/架构层 | 流量特征匹配 | 浏览器执行层 | 代码根治层 |
| 覆盖面 | 广(所有缓存层) | 仅流经 WAF 流量 | 仅浏览器端 | 仅应用代码 |
| 误报 | 无(配置生效) | 有(规则误判) | 低(策略过严报错) | 低(若编码正确) |
| 维护成本 | 中(需审计缓存键) | 高(规则更新) | 低 | 中 |
| 适用阶段 | 架构/部署期 | 运行时兜底 | 开发/部署期 | 开发期根治 |
